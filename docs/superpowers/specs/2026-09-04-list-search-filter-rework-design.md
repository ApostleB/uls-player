# 목록 검색·필터 개편 설계

## 1. 목표

검색창을 메뉴바에서 목록 화면으로 되돌리고, 그 자리에 검색 범위 선택기와 확장자 필터를 더한다. 목록 상단의 중복된 제목을 없애고 `가져오기` 버튼을 검색 영역 아래로 옮긴다.

검색창이 메뉴바에 있는 동안 생긴 구조적 부담 — 같은 URL을 두 곳에서 고치는 것 — 을 함께 걷어낸다. 이 개편의 절반은 코드 삭제다.

## 2. 메뉴바 검색 제거

메뉴바 검색은 모든 화면에 떠 있어야 하는 대신, 목록 화면의 태그·기간 필터와 같은 쿼리스트링을 함께 고쳐야 했다. `goto`가 비동기라 두 writer가 겹치면 나중 것이 앞선 변경을 못 본 스냅샷으로 덮어쓰는 경합이 있었고, 그것을 막으려고 모듈 레벨 레지스트리(`listFilterBridge.ts`)를 두어 목록이 떠 있는 동안은 메뉴바가 `goto`를 부르지 않게 했다.

검색창이 목록으로 오면 writer가 처음부터 하나다. 레지스트리도, 병합 함수도 필요 없다.

| 대상 | 처리 |
|---|---|
| `src/lib/listFilterBridge.ts` | 삭제 |
| `src/lib/searchQuery.ts`, `src/lib/searchQuery.test.ts` | 삭제 — `mergeSearchQuery`는 `+layout.svelte`에서만 쓰였다 |
| `+layout.svelte`의 `search()`와 `goto`·두 모듈 import | 삭제 (`page`는 `pathname`을 넘기느라 남는다) |
| `MenuBar.svelte`의 입력·디바운스·`q`/`onsearch` props | 삭제 |
| 목록 페이지의 `<h1 class="h2">ULS Player</h1>` | 삭제 |

`+layout.svelte`는 `<MenuBar pathname={page.url.pathname} />`만 남는다. `page`는 `pathname`을 넘기느라 계속 필요하다.

**유지되는 것:** 필터를 URL에 반영하는 `goto`는 여전히 목록 화면의 이펙트 하나뿐이다. 이 규칙은 약해지지 않고, writer가 하나로 줄어 더 단단해진다. `untrack`으로 URL → 필터 이펙트의 자기 참조를 끊는 구조도 그대로다 — `goto`가 비동기라는 사실은 변하지 않는다.

## 3. 검색 범위

### 3.1 모델

`Filter`에 `scope`를 더한다.

```ts
export type SearchScope = 'all' | 'title' | 'description' | 'tags';
```

`applyFilter`가 범위에 따라 검사 대상을 고른다.

| 범위 | 대상 |
|---|---|
| `all` | 제목, 설명, 태그 — 하나라도 걸리면 통과 |
| `title` | 제목만 |
| `description` | 설명만 |
| `tags` | 각 태그 문자열에 부분 일치 |

`tags` 범위의 부분 일치는 태그 칩 필터의 정확 일치와 다르다. "회의"로 "회의록"이 걸린다. 둘은 서로를 대체하지 않는다 — 칩은 아는 태그를 고르는 것이고, 검색은 기억나는 조각으로 찾는 것이다.

검색어 비교는 지금처럼 `trim()` 후 소문자 비교다.

### 3.2 URL

`scope=title` 형태로 싣고, 기본값 `all`은 생략한다. `q=`만 있는 기존 링크는 `all`로 해석되어 그대로 동작한다. `filterFromParams`는 아는 값이 아니면 `all`로 떨어뜨린다 — `tagMode`가 `mode=or`가 아니면 `and`로 떨어지는 것과 같은 규칙이다.

### 3.3 입력 동작

메뉴바에서 쓰던 것을 그대로 가져온다: 250ms 디바운스, Enter는 대기를 건너뛴다, 한글 조합 중 Enter는 `isComposing`으로 무시한다.

범위를 바꾸면 디바운스 없이 즉시 반영한다. 선택이지 타이핑이 아니다.

### 3.4 지금은 비어 있는 범위

269개 중 설명이 있는 것 0개, 태그가 있는 것도 0개다. `description`과 `tags` 범위는 현재 데이터로 항상 0건이다. 이는 결함이 아니라 아직 채우지 않았다는 뜻이며, 인라인 편집으로 채워나가면 의미가 생긴다. **테스트는 설명·태그가 있는 픽스처를 직접 만들어 검증한다** — 실데이터가 비어 있다고 검증을 미루면 채워지는 시점에 아무도 확인하지 않는다.

## 4. 확장자 필터

### 4.1 무엇을 거르나

녹음 하나의 확장자 집합은 **원본 확장자와 변환 완료된 포맷 이름의 합집합**이다.

```
files: { original: {ext:'qta'}, mp3: {...}, wav: {...} }  →  {qta, mp3, wav}
```

현재 데이터는 `{qta,mp3,wav}` 215개, `{m4a,mp3,wav}` 54개다. `mp3`·`wav`는 지금 전부가 갖고 있어 걸러내지 못하지만, 이 필터의 용도는 "이 녹음이 가진 확장자에 X가 있는가"이므로 변환이 깨진 녹음이 생기면 그때 걸러낸다.

### 4.2 AND 의미

여러 개를 고르면 **모두 가진 것**만 남는다. 모드 토글은 두지 않는다.

OR이면 `qta+m4a`도 `mp3+wav`도 전체를 뜻해 무의미해진다 — 원본 확장자는 녹음마다 하나뿐이고 변환 포맷은 거의 전부가 갖고 있기 때문이다. AND면 `qta+mp3`가 "qta 원본이면서 mp3 변환이 끝난 것"으로 실제로 좁혀진다. 태그 필터의 기본값도 `and`라 일관된다.

`qta`와 `m4a`를 함께 고르면 0건이 된다. 어떤 녹음도 원본 확장자를 둘 가질 수 없으니 정직한 결과이며, 각 칩의 개수 배지가 이유를 보여준다.

### 4.3 UI와 URL

태그 칩과 같은 모양 — 확장자 이름과 개수 배지, 누르면 토글.

**개수는 화면에서 `recordings`로부터 파생한다**(`$derived`). 태그 개수는 서버가 `allTags`로 세어 내려보내지만 확장자는 그럴 필요가 없다 — 목록 전체가 이미 화면에 내려와 있고, 태그와 달리 확장자는 UI로 바뀌지 않아 서버가 권위를 가질 이유가 없다. `+page.server.ts`는 건드리지 않는다.

정렬은 원본 확장자 먼저, 그다음 변환 포맷이며 각 묶음 안에서는 개수 내림차순이다. 원본이 사용자가 실제로 구분하려는 값이고, 변환 포맷은 거의 전부가 공유해 뒤에 있어도 찾기 쉽다.

URL은 `ext=qta&ext=mp3`. 태그와 같이 값마다 파라미터를 하나씩 붙인다.

목록에 확장자가 하나뿐이면 칩 줄 자체를 숨긴다 — 고를 것이 없는 필터는 자리만 차지한다. 태그 칩이 `{#if tags.length}`로 같은 판단을 하고 있다.

## 5. 배치

```
┌──────────────────────────────────────────┐
│  [검색어………………]  [전체▾]     249 / 269   │   검색 카드
└──────────────────────────────────────────┘
                              [ 가져오기 ]
┌──────────────────────────────────────────┐
│  기간 [____] ~ [____]           [초기화]  │   필터 카드
│  확장자  (qta 215) (m4a 54) (mp3 269) …   │
│  태그   [모두포함|하나라도]  (칩…)         │
└──────────────────────────────────────────┘
```

검색과 필터를 **다른 카드로 나눈다.** 검색은 매번 치는 것이고 기간·확장자·태그는 가끔 여는 것이다. 한 카드에 넣으면 검색창이 필터 더미에 묻힌다.

`249 / 269` 카운트는 검색 카드로 옮긴다. 결과 개수는 검색어를 치면서 보는 값이다.

`가져오기`는 검색 카드 아래, 오른쪽 정렬이다.

`초기화`는 필터 카드에 남되 **검색어와 범위까지 함께 비운다.** 지금도 그렇게 동작하며(`EMPTY_FILTER` 전체로 되돌린다), 그 동작을 지키는 e2e가 있다. `EMPTY_FILTER`에 `scope: 'all'`과 `ext: []`를 더한다.

## 6. 컴포넌트 경계

`FilterBar.svelte`가 검색까지 떠안으면 한 파일이 다섯 가지를 다루게 된다. 나눈다.

| 파일 | 책임 |
|---|---|
| `SearchBar.svelte` (신규) | 검색어 입력, 디바운스, 범위 선택기, 결과 카운트 |
| `FilterBar.svelte` (수정) | 기간, 확장자 칩, 태그 칩, 초기화 |

둘 다 `filter`를 `$bindable`로 받는다. 지금 `FilterBar`가 쓰는 방식과 같고, 목록 화면의 필터 → URL 이펙트가 두 컴포넌트의 변경을 똑같이 받는다.

디바운스가 `SearchBar` 안으로 들어가므로, 범위 선택과 검색어 입력이 서로 다른 타이밍 규칙을 갖는다는 사실(3.3절)이 한 파일 안에서 읽힌다.

## 7. 테스트

| 대상 | 확인 | 깨뜨리는 뮤테이션 |
|---|---|---|
| 범위 `title` | 설명에만 있는 낱말로는 안 걸린다 | 범위 무시하고 항상 제목+설명 검사 시 실패 |
| 범위 `description` | 설명에 있는 낱말로 걸린다 | 설명을 대상에서 빼면 실패 |
| 범위 `tags` | 태그의 일부 문자열로 걸린다 | 부분 일치를 정확 일치로 바꾸면 실패 |
| 범위 `all` | 셋 중 아무 곳에나 있으면 걸린다 | 대상 하나를 빼면 실패 |
| 범위 URL 왕복 | `scope=title`이 실리고 `all`은 안 실린다 | 기본값도 실으면 실패 |
| 알 수 없는 scope | `scope=xyz`가 `all`로 떨어진다 | 그대로 통과시키면 실패 |
| 확장자 AND | 두 개를 고르면 둘 다 가진 것만 남는다 | OR로 바꾸면 실패 |
| 확장자 집합 | 원본 확장자와 변환 포맷이 모두 후보에 든다 | 한쪽만 보면 실패 |
| 확장자 칩 순서 | 원본 확장자가 변환 포맷보다 앞에 온다 | 개수 순으로만 정렬하면 실패 |
| 확장자 칩 숨김 | 확장자가 한 종류면 칩 줄이 없다 | 항상 그리면 실패 |
| 디바운스 | 연속 입력 중에는 URL이 안 바뀌고, 멈추면 한 번 바뀐다 | 디바운스 제거 시 실패 |
| Enter 즉시 반영 | Enter는 대기를 건너뛴다 | Enter 처리 제거 시 실패 |
| 한글 조합 | 조합 중 Enter는 커밋하지 않는다 | `isComposing` 검사 제거 시 실패 |
| 범위 전환 | 범위를 바꾸면 디바운스 없이 즉시 반영된다 | 범위도 디바운스에 태우면 실패 |
| 초기화 | 검색어·범위·확장자·태그·기간이 모두 비워진다 | 일부만 비우면 실패 |
| 메뉴바 | 메뉴바에 입력 요소가 없다 | 검색창을 남기면 실패 |

**기존 e2e 4개를 다시 쓴다.**

| 기존 테스트 | 처리 |
|---|---|
| 메인에서 메뉴바로 검색하면 목록으로 이동하며 걸러진다 | 삭제 — 동선 자체가 없어진다 |
| 태그 클릭과 메뉴바 검색이 겹쳐도 서로의 변경을 지우지 않는다 | 삭제 — 경합이 성립하지 않는다 |
| 목록에서 태그를 고른 뒤 검색해도 태그 필터가 유지된다 | 목록 검색창 상대로 다시 쓴다 |
| 목록에서 초기화하면 검색창도 함께 비워진다 | 목록 검색창 상대로 다시 쓴다 |

뒤의 둘은 실제 버그를 잡았던 테스트다. 대상이 바뀔 뿐 없애지 않는다.

배치나 접근 이름을 재는 테스트는 `app.css`를 직접 import하는 별도 파일에 둔다 — 이 프로젝트의 컴포넌트 테스트는 `+layout.svelte` 없이 페이지를 단독 마운트해 Tailwind가 적용되지 않는다.

## 8. 이 문서가 다루지 않는 것

- **재생 길이 필터** — 처음 요청에 있었으나 뺐다. 269개 중 202개가 3~5분에 몰려 있어 어떤 구간을 나눠도 거의 걸러지지 않는다
- **제목·설명 인라인 편집 정리**(완료 버튼, Enter 저장, 입력창 축소) — 별도 계획에 이미 쓰여 있다. 목록 헤더 근처를 함께 건드리므로 이 개편 뒤에 얹는다
- **메인 페이지 카드 3종** — 별도 스펙
- **파일 상세정보**, **음원 편집** — 별도 스펙
- **목록의 지역 `fmt`가 59.6초를 `0:60`으로 찍는 문제** — 알려진 선행 버그, 별도 커밋 대상
