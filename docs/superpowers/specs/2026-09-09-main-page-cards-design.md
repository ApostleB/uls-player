# 메인 페이지 카드 설계

## 1. 목표

메인 페이지(`/`)는 지금 제목과 두 개의 링크뿐이다. 여기에 자주 듣는 것과 방금 들어온 것을 바로 볼 수 있는 카드를 놓는다.

## 2. 이번에 만들지 않는 것 — 최다 재생 카드

원래 요청은 카드 셋이었다. 세 번째인 **"최근 가장 많이 재생한 음악 TOP5"(오늘/1주일/1개월/6개월 전환)는 이번 범위에서 뺀다.**

기간별 집계를 하려면 재생할 때마다 시각이 찍힌 개별 이벤트를 남겨야 한다. 단순 카운터로는 "지난 1주일"을 계산할 수 없다. 그러면 "무엇을 재생으로 칠 것인가"(버튼을 눌렀는가 / 몇 초 이상 들었는가), 이벤트를 언제까지 보관할 것인가, JSON 파일에 무한히 쌓이는 것을 어떻게 정리할 것인가를 모두 정해야 한다 — 카드 하나가 아니라 별도의 데이터 수집 기능이다.

나머지 둘은 그런 부담이 없다. 즐겨찾기는 필드 하나, 최근 추가는 이미 있는 데이터다. 먼저 쓸 수 있게 만들고, 재생 기록은 별도 스펙으로 다룬다.

## 3. 데이터 — `favoritedAt`

`Recording`에 필드 하나를 더한다.

```ts
/** 즐겨찾기로 지정한 시각. null이면 즐겨찾기가 아니다. */
favoritedAt: string | null;
```

**불리언이 아니라 시각인 이유:** 카드가 "최근에 지정한 5개"를 뽑아야 한다. 불리언이면 순서를 알 수 없어 정렬용 필드가 또 필요해진다. 하나로 둘 다 답한다.

기존 녹음에는 이 필드가 없다. 읽을 때 `?? null`로 채우면 마이그레이션 없이 동작한다 — 이 저장소는 스키마 버전을 올리는 대신 읽는 쪽에서 기본값을 채우는 방식을 이미 쓰고 있다.

**즐겨찾기 개수에 제한을 두지 않는다.** "최대 5개"는 카드에 보이는 수이지 지정할 수 있는 수가 아니다. 지정하려다 막히는 경험을 만들지 않고, 나중에 목록 화면에서 즐겨찾기로 거르는 길도 열어둔다.

## 4. 지정하는 곳

목록 행의 선택 체크박스 옆에 별 버튼을 둔다.

서버 API에 op을 하나 더한다.

```ts
{ op: 'favorite'; id: string; favorite: boolean }
```

**시각은 서버가 찍는다.** 클라이언트가 `favoritedAt` 값을 직접 보내면 아무 시각이나 넣을 수 있어 "최근 5개"의 순서를 조작할 수 있다. 기존 `patch` op(제목·설명·태그·북마크를 받는다)에 얹지 않고 따로 두는 이유가 이것이다 — `patch`는 클라이언트가 준 값을 그대로 저장하는 op이고, 이건 서버가 값을 정하는 op이다.

`favorite: false`면 `favoritedAt`을 `null`로 되돌린다.

## 5. 카드 둘

| 카드 | 기준 | 개수 |
|---|---|---|
| 즐겨찾기 | `favoritedAt` 내림차순 | 5 |
| 최근 추가된 음악 | `createdAt` 내림차순 | 5 |

메인 페이지에는 지금 `load`가 없다. `+page.server.ts`를 새로 만들어 목록을 읽고 두 배열을 계산해 내려보낸다 — 화면이 전체 목록을 받아 거르는 것이 아니라, 필요한 10개만 내려간다.

삭제된 녹음(`deletedAt`)은 양쪽 모두에서 제외한다.

**즐겨찾기가 하나도 없으면 그 카드를 그리지 않는다.** 빈 카드는 자리만 차지한다. 목록 화면의 태그 칩과 확장자 칩이 이미 같은 규칙을 쓴다. 최근 추가 카드는 녹음이 하나라도 있으면 항상 내용이 있으므로 같은 처리가 필요 없다.

## 6. 카드에서 누르면

제목을 누르면 `/recordings?play=<id>`로 이동한다. 목록 화면이 그 파라미터를 보면 해당 행을 선택하고 재생 의사를 보낸다 — 행 클릭과 같은 경로(`selectRow`)를 탄다.

제목만 보여주고 아무 일도 하지 않으면 카드가 반쪽이다. 어디에 있는지 알려주고 끝내는 것과, 바로 듣게 해주는 것의 차이다.

`play` 파라미터는 **처리한 뒤 URL에서 지운다.** 남겨두면 새로고침이나 뒤로 가기에서 다시 재생이 걸린다.

지우는 방법으로 새 내비게이션을 추가하지 않는다. 목록의 필터 → URL 이펙트가 `filterToParams(filter)`로 쿼리스트링을 **처음부터 다시 만들어** `goto`하므로, 필터에 없는 `play`는 그 다음 갱신에서 자연히 빠진다. 이 화면에서 URL을 쓰는 `goto`가 하나뿐이라는 규칙을 지키기 위해서다 — 두 번째 writer를 만들면 이 저장소가 이미 한 번 겪은 경합이 돌아온다.

**필터가 걸려 있어도 재생은 된다.** 선택과 재생은 `selectedId`·`playRequest`로 이뤄지고 필터는 목록에 무엇을 그릴지만 정하므로, 고른 녹음이 현재 필터에 안 걸리면 행은 안 보이지만 재생기에는 뜬다. 메인 카드에서 올 때는 필터가 없으므로 실제로는 드문 경우이고, 이 동작을 예외 처리하지 않는다 — 재생하러 온 사람에게 재생을 안 해주는 쪽이 더 나쁘다.

없는 id가 들어오면 아무 일도 하지 않는다. 오류를 띄우지 않는다 — 링크가 오래됐거나 그 사이 삭제된 것뿐이고, 목록은 정상적으로 보여주는 것이 맞다.

## 7. 테스트

| 대상 | 확인 | 깨뜨리는 뮤테이션 |
|---|---|---|
| `favorite` op | 지정하면 `favoritedAt`에 시각이 들어간다 | op 제거 시 실패 |
| 서버가 시각을 정한다 | 클라이언트가 보낸 시각은 무시된다 | 클라이언트 값을 쓰면 실패 |
| 해제 | `favorite:false`면 `favoritedAt`이 null이 된다 | 해제 처리 제거 시 실패 |
| 하위 호환 | 필드가 없는 기존 녹음도 읽힌다 | `?? null` 제거 시 실패 |
| 즐겨찾기 카드 | `favoritedAt` 내림차순 5개만 | 정렬·개수 바꾸면 실패 |
| 최근 추가 카드 | `createdAt` 내림차순 5개만 | 같음 |
| 삭제 제외 | `deletedAt`이 있는 녹음은 어느 카드에도 없다 | 필터 제거 시 실패 |
| 빈 즐겨찾기 | 하나도 없으면 그 카드가 없다 | 항상 그리면 실패 |
| `?play=<id>` | 그 녹음이 선택되고 재생된다 | 파라미터 무시 시 실패 |
| 파라미터 정리 | 처리 후 URL에서 `play`가 사라진다 | 지우지 않으면 실패 |
| 없는 id | 아무 일도 일어나지 않고 목록은 정상이다 | 오류를 띄우면 실패 |

배치나 접근 이름을 재는 테스트는 `app.css`를 직접 import하는 파일에 둔다 — 이 프로젝트의 컴포넌트 테스트는 `+layout.svelte` 없이 페이지를 단독 마운트해 Tailwind가 적용되지 않는다.

## 8. 이 문서가 다루지 않는 것

- **최다 재생 카드와 재생 기록 수집**(2절) — 별도 스펙
- **목록 화면에서 즐겨찾기로 거르기** — `favoritedAt`이 생기면 가능해지지만 이번 요청에 없다
- **재생기에서 즐겨찾기 지정** — 목록 행에서만 지정한다. 필요해지면 그때 더한다
- **파일 상세정보**, **음원 편집** — 각각 별도 스펙
