# 변환·기동 속도 개선과 같은 포맷 복사 설계

## 1. 목표

Windows 데스크톱 앱에서 두 가지가 느리다는 보고를 받았다 — **켜지기까지**, 그리고 **변환**. 둘을 빠르게 하고, 원본이 이미 출력 포맷이면 변환하지 않고 복사한다.

이 문서는 Electron 패키징 브랜치(`feat/electron-windows-package`) 위에 쌓인다. 3·4·5절이 그 브랜치의 셸 코드를 고친다.

## 2. 조사 결과 — 무엇이 실제로 느린가

추측으로 고치지 않기 위해 먼저 쟀다. 측정 환경은 12코어 macOS, 원본은 실제 라이브러리의 QTA(3분 40초, 48kHz 스테레오 AAC)다.

### 변환

파일 하나의 파이프라인은 **ffmpeg 프로세스를 4번 실행하고 원본 전체를 3번 디코드**한다.

| 단계 | 시간 |
|---|---|
| ffprobe | 0.04초 |
| **mp3 변환** | **1.64초** |
| wav 변환 | 0.19초 |
| 파형 | 0.16초 |

**mp3 인코딩 하나가 파일당 시간의 80%다.** 세 번 디코드하는 낭비는 한 번으로 합쳐도 0.45초 줄어드는 데 그친다.

mp3 인코더 설정별로 다시 쟀다.

| 설정 | mp3 변환 |
|---|---|
| 현재 (192k, 44.1kHz 리샘플, 2ch) | 1.78초 |
| 리샘플 없이 48kHz 그대로 | 1.65초 |
| 현재 + `compression_level 7` | **0.81초** |
| 현재 + `compression_level 9` | 0.80초 |

`compression_level`은 LAME이 원본에서 어떤 소리를 남길지 고르는 계산의 정밀도다. 비트레이트는 그대로 두고 이것만 낮춰도 2.2배 빨라진다.

그리고 **동시 변환 수가 4로 고정**돼 있다. 24개 배치로 쟀다.

| 동시 수 / 인코더 | 24개 |
|---|---|
| 4 / 기본 (현재) | 15.1초 |
| 12 / 기본 | 9.9초 |
| 4 / 레벨 7 | 8.8초 |
| 12 / 레벨 7 | 7.6초 |

동시 수를 3배로 올려도 1.5배에 그치는 것은 12코어 중 일부가 효율 코어이고, wav 쓰기(파일당 약 20MB)가 겹치기 때문으로 보인다.

**Windows에서만 드러날 수 있는 몫이 하나 더 있다.** ffmpeg를 실행할 때마다 공유 DLL 182MB를 불러오고, Windows는 프로세스 생성이 macOS보다 비싸다. 파일 310개면 ffmpeg가 1,240번 뜬다. 이 맥에서는 잴 수 없다.

### 기동

**앱 자체는 빠르다.** 실제 라이브러리 309개의 복사본을 두고, 배포와 같은 방식(Electron 바이너리를 Node로)으로 서버만 띄워 쟀다.

| 측정 | 시간 |
|---|---|
| 서버 첫 응답 (콜드) | 0.35초 |
| 서버 첫 응답 (웜) | 0.10초 |
| `GET /` | 2ms |
| `GET /recordings` (481KB) | 28ms |

Electron e2e 기준으로 창이 뜨고 메인 화면이 보이기까지 약 0.85초다.

그런데 셸은 **서버가 응답할 때까지 기다렸다가 그제야 창을 만든다.** 서버 기동과 Chromium 창 생성이 차례로 이어져 있다. Windows에서는 창 생성이 더 비싸다.

배포물 580MB 가운데 **언어 파일이 48MB**다. 이 앱은 한국어 화면 하나뿐이다.

## 3. 원본이 이미 출력 포맷이면 복사

러너의 포맷별 루프에서 `convert`를 부르기 전에 "원본이 이미 이 포맷인가"를 판정한다. 맞으면 변환 대신 원본을 출력 경로로 **복사**한다. 파형은 지금처럼 원본에서 만든다.

### 판정 기준

**확장자가 아니라 ffprobe가 본 실제 내용으로** 판정한다. **컨테이너와 코덱이 둘 다** 맞아야 복사한다.

| 출력 | 복사 조건 |
|---|---|
| mp3 | 컨테이너 `mp3` + 코덱 `mp3` |
| wav | 컨테이너 `wav` + 코덱이 `pcm_`로 시작 |
| 그 밖의 포맷 | 복사하지 않는다 (항상 변환) |

**둘 다 봐야 하는 이유:**

- 확장자만 보면, 이름만 `.mp3`인 AAC 파일이 "mp3"로 복사돼 재생되지 않는 파일이 생긴다.
- 코덱만 보면, AIFF(`pcm_s16be`)가 `.wav` 이름으로 복사돼 실제로는 AIFF인 "wav"가 생긴다.

판정은 순수 함수 하나로 떼어 단위 테스트한다. 컨테이너 이름이 필요하므로 `ProbeResult`에 `formatName`(ffprobe의 `format.format_name`)을 더한다. 코덱은 이미 `codecName`으로 있다.

### 설정보다 우선한다

사용자 결정이다. 원본 포맷이 출력 포맷과 같으면, 그 출력에 설정된 비트레이트·샘플레이트·채널 수를 따르지 않고 원본 그대로 복사한다.

예를 들어 48kHz 스테레오 wav 원본은 설정된 44.1kHz 모노로 바뀌지 않는다. wav 출력의 규격이 원본마다 달라진다. 128kbps mp3 원본을 192kbps로 다시 인코딩해 봐야 음질은 나아지지 않고 한 번 더 손실만 생기므로, mp3 쪽은 복사가 순수하게 이득이다.

### 디스크

원본은 `media/original/`에, 복사본은 `media/<포맷>/`에 한 벌씩 따로 둔다. mp3·wav 원본은 디스크를 두 배 쓴다. 두 파일이 서로 독립이라 한쪽을 지워도 다른 쪽이 남는다.

### 재시도

복사도 변환과 같은 규칙을 따른다. 이미 `done`인 포맷은 건너뛰고, 복사가 실패하면 그 포맷만 `failed`로 남긴다. 러너가 이미 갖고 있는 포맷별 결과 기록과 재시도 규칙을 그대로 쓴다.

## 4. mp3 인코더 레벨 설정

`FormatSpec`에 필드 하나를 더한다.

```ts
/** LAME의 인코딩 알고리즘 정밀도(0~9). null이면 ffmpeg에 넘기지 않는다. */
compressionLevel: number | null;
```

기존 `MP3_BITRATE`·`MP3_SAMPLE_RATE`와 같은 방식으로 `${포맷}_COMPRESSION_LEVEL` 환경변수를 읽는다. mp3라면 `MP3_COMPRESSION_LEVEL`이다.

**기본값은 `null`이다.** `null`이면 `convert`가 `-compression_level`을 아예 넘기지 않으므로 **지금과 똑같이 인코딩된다.** 서버 배포도 데스크톱도 기본 동작이 바뀌지 않는다 — 사용자 결정이다. 빠르게 하고 싶으면 `MP3_COMPRESSION_LEVEL=7`을 지정한다.

**검증:** 0~9의 정수여야 한다. 벗어나면 다른 설정 오류처럼 기동 시 거부한다. 조용히 무시하면 사용자는 설정이 먹었다고 믿은 채 느린 변환을 계속 보게 된다.

wav(`pcm_s16le`)에는 이 옵션의 의미가 없다. 필드는 모든 포맷에 두되 wav 기본값도 `null`이라 넘어가지 않는다 — 비트레이트가 wav에서 `null`인 것과 같은 방식이다.

## 5. 동시 변환 수 — 데스크톱만

셸이 서버에 넘기는 환경변수에 기본값을 하나 더한다.

```
CONVERT_CONCURRENCY = max(1, 코어 수 − 1)
```

- **사용자가 지정한 값이 이긴다.** `buildServerEnv`의 기존 규칙(`DATA_DIR` 등은 바깥이 이긴다)을 그대로 따른다.
- **서버 배포의 기본값 4는 바꾸지 않는다.** 서버가 몇 코어인지, 동시에 무엇이 도는지 이 앱은 모른다.
- **하나를 남기는 이유:** libmp3lame은 프로세스당 코어 하나를 쓴다. 코어를 전부 쓰면 변환하는 동안 재생과 화면이 끊긴다.

코어 수는 `buildServerEnv`의 인자로 받는다. `platform`을 인자로 받는 것과 같은 이유다 — `os.availableParallelism()`을 직접 부르면 1코어나 64코어 경우를 테스트할 수 없다.

## 6. 창 먼저 띄우기

```
지금:  서버 fork ──대기──▶ 응답 ──▶ 창 생성 ──▶ 앱 표시
변경:  서버 fork ──대기──▶ 응답 ──▶ 앱으로 이동
       창 생성 ─▶ 로딩 화면 표시  ┘
```

`app.whenReady()` 직후 창을 만들어 로딩 화면을 띄우고, **동시에** 서버를 띄운다. 서버가 응답하면 창을 앱 주소로 옮긴다.

**로딩 화면**은 파일 없이 인라인 페이지(`data:` URL)로 띄운다. 앱 이름과 "여는 중" 정도만 담는다. 창의 `backgroundColor`를 OS 테마(`nativeTheme.shouldUseDarkColors`)에 맞춰, 창이 뜨는 순간 흰 화면이 번쩍이지 않게 한다.

**실패 처리는 그대로다.** 서버가 기동에 실패하거나 도중에 죽으면 오류 대화상자를 띄우고 앱을 끝낸다. 달라지는 것은 그 대화상자가 이미 떠 있는 로딩 창 위에 뜬다는 점뿐이다.

**보안 설정은 그대로다.** 로딩 페이지도 같은 창이므로 `contextIsolation`·`sandbox`·preload가 똑같이 적용된다. 로딩 페이지에는 링크가 없고, 앱 주소로의 이동은 프로그램이 부르는 `loadURL`이라 `will-navigate` 가드와 무관하다.

## 7. 언어 파일 정리

`electron-builder.yml`에 한 줄을 더한다.

```yaml
electronLanguages: [ko, en-US]
```

`locales/`가 48MB에서 1~2MB로 준다. portable exe가 켤 때마다 푸는 양과, Windows Defender가 새 파일로 보고 검사하는 양이 그만큼 줄어든다. `en-US`는 Chromium이 한국어 리소스를 못 찾을 때의 대비로 남긴다.

## 8. 테스트

| 대상 | 확인 | 깨뜨리는 변경 |
|---|---|---|
| 판정 함수 | mp3 컨테이너 + mp3 코덱 → 복사 | 판정 제거 시 실패 |
| 판정 함수 | 이름만 `.mp3`인 AAC(컨테이너 `mov,mp4…`) → 변환 | 확장자로 판정하면 실패 |
| 판정 함수 | wav 컨테이너 + `pcm_s16le` → 복사 | — |
| 판정 함수 | AIFF(`pcm_s16be`) → 변환 | 코덱만 보면 실패 |
| 판정 함수 | QTA(AAC) → mp3·wav 모두 변환 | — |
| 판정 함수 | 모르는 포맷 이름 → 변환 | 기본값을 복사로 두면 실패 |
| 러너 | 판정이 맞으면 `convert`가 불리지 않고, 출력이 원본과 바이트 단위로 같다 | 복사 분기 제거 시 실패 |
| 러너 | 판정이 틀리면 지금처럼 `convert`가 불린다 | — |
| 설정 | `MP3_COMPRESSION_LEVEL` 미지정 → `null` | 기본값을 바꾸면 실패 |
| 설정 | `10`, `-1`, `abc` → 기동 거부 | 범위 검사 제거 시 실패 |
| 변환 | 레벨이 `null`이면 인자에 `-compression_level`이 없다 | 항상 넘기면 실패 |
| 변환 | 레벨 `7`이면 `-compression_level 7`이 들어간다 | — |
| 셸 env | 코어 12 → `11`, 코어 1 → `1` | `−1`이나 최솟값 제거 시 실패 |
| 셸 env | 바깥에 `CONVERT_CONCURRENCY`가 있으면 그 값 | 덮어쓰면 실패 |
| Electron e2e | 첫 화면이 로딩 페이지이고, 그다음 앱이 뜬다 | 창을 서버 뒤로 되돌리면 실패 |
| 패키징 | `locales/`에 `ko`·`en-US`만 남는다 | 설정 제거 시 실패 |

**변경 전후를 같은 24개 배치로 재서 문서에 수치로 남긴다.** 이 설계의 목적이 속도이므로, 테스트 통과만으로는 목적을 이뤘는지 알 수 없다.

## 9. 이 문서가 다루지 않는 것

- **ffmpeg 직접 빌드(필요한 코덱만 넣어 182MB → 15MB 안팎)** — 사용자가 고른 범위이지만 다음 스펙으로 나눈다. macOS에서 Windows용 ffmpeg를 크로스 빌드하는 툴체인 작업이고, 이 맥에서는 만든 바이너리를 실행해볼 수 없어 검증 방법부터 따로 설계해야 한다.
- **ffmpeg 한 번 실행으로 mp3·wav·파형을 합치기** — 사용자가 고르지 않았다. 러너의 포맷별 결과 기록과 재시도 규칙을 다시 짜야 하는 작업이다.
- **데스크톱에서 업로드 칸 숨기기**, **mp3 녹음일자 보완** — 사용자가 고르지 않았다.
